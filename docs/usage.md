# Как пользоваться yokemate

Главный чат — сессия pi в корне репозитория, открытая в herdr. Команды ниже набираются в нём. Стадию в базе (`yokemate.db`) записывает тот runtime, где родился результат: команды сами проверяют identity, допустимость перехода и текущую стадию. Главный чат остаётся входом для ремонта (`pnpm stage … --force`); do и ship работают фоновыми coordinator-ами и не создают вкладок.

## Где открывается режим

`/plan`, `/review`, `/worklog`, `/note` и `/research` по умолчанию открывают новый herdr tab. Для split от вызывающей pane добавь `--split` до первого `--`: `/plan --split YM-1`, `/review YM-1 --split`. `/split plan YM-1` остаётся compatibility alias для `/plan --split YM-1`; другие режимы используют только свой параметр. `--tab` нет. После `--` все слова буквальные: `/note тема -- --split --model x` откроет tab и передаст эти слова в тему. Разговорную панель закрываешь ты; исключение — успешный rework из review: parent закрывает только её после ACK нового `/do`. `/do` и `/ship` остаются фоновыми.

Явный `/plan KEY1 KEY2` одним parent-owned list run сначала резервирует все допустимые ключи, затем поднимает отдельный tab на каждый ключ под общим лимитом; `/plan --split KEY1 KEY2` и `/split plan KEY1 KEY2` — отдельный split на ключ от той же вызывающей pane. У каждого worker только свой ключ, identity и отдельный terminal result в parent pane; после всех terminal results приходит один aggregate в исходном порядке. Общие explicit `--model` и literal tail после `--` передаются каждому. Отказ/ошибка одного ключа не мешает остальным. Single-key и problem/mixed input остаются одной surface; пакет, созданный после одного интервью, не разделяется.

## Подключение проекта

```bash
pnpm add-project <путь-к-клону> --tracker <org:KEY> [--model <m>] [--model <мод>=<m> …] [--figma <mcp>] [--figma-file <url>] [--subsystem <значение>]
```

Паспорт репозитория попадает в базу, знание из его `.yoke/` импортируется один раз в `home/knowledge/<org>/<repo>/`. Scalar `--model` задаёт concrete default паспорта; без него команда берёт именно `pool.do`, валидирует и записывает одинаковое concrete значение в SQLite и `home/projects.json`. Токен `--model do=<m>` остаётся только mode override и default не заменяет.

Паспорта живут и в манифесте `home/projects.json`: `pnpm export-projects` выгружает их туда разом (первое заполнение и ремонт), `pnpm import-projects [--only <org/repo>]` восстанавливает клоны в `projects/<org>/<repo>` и паспорта из манифеста — существующие паспорта не трогаются. Новую машину поднимает `scripts/bootstrap.sh` — идемпотентен, что остаётся ручным (`.env.local`, `home/`, `gh auth login`, ключи), называет в финальной сводке. `home/` поднимается клоном по адресу из `YOKEMATE_HOME_REMOTE`; без переменной bootstrap его не создаёт и называет шаг в сводке.

## Обзор

- `pnpm on-me [org] [PROJECT] [--repo <name>] [--stage <values>] [--stages] [--all] [--verbose]` — неразрешённые тикеты на мне, прямо из трекеров, по репозиториям.
- `pnpm queue [planned|me]` — локальная очередь; синк с трекерами при каждом чтении.
- `pnpm warmup` / `/warmup` — дайджест пула (очередь, живые `work/`, хвост журнала), офлайн и без синка; хук `session_start` вставляет его сам на старте сессии.

## Круг тикета

1. `/plan ACME-342 [ACME-343 …] [заметка]` или `/plan <проблема>` — в новом tab по умолчанию (`--split` — split): разведка кода и написание плана — в сабагентах (`plan-scout`, `plan-writer`), вопросы к тебе — в ленте режима, по одному с выбором опций (немного вопросов, только меняющие реализацию, каждый с рекомендацией). Вход с проблемой сначала проходит интервью и валидацию пакета («Заводим?») — тикеты создаются в YouTrack до планов. Итог: детальный план в `home/knowledge/<org>/<proj>/ai/<KEY>-<slug>/`, по которому /do работает без переспросов — шаги с файлами и проверкой на каждый, допущения, out of scope, критерии приёмки; стадию `planned` записывает `pnpm plan`. Нерешаема на данных тикета — плана нет, отчёт называет недостающее. Для нескольких планирований рядом используй `/plan --split <аргументы>`; `/split plan <аргументы>` — compatibility alias. Панель закрываешь ты.

   Если рантайм сообщил, что полный финал `plan-scout` сохранён как recovery candidate после ошибки транспорта, MAIN может принять только его точной typed-командой `/break-glass <KEY> accept-plan-scout-input --candidate <UUID> --reason <безопасная причина>`. Перед подтверждением сверяй ticket, source run, размер, payload/failure hashes и `failed-transport-envelope`. Разрешение одноразовое, живёт пять минут, оставляет все остальные проверки обязательными и возобновляет только текущий живой `/plan`; полученный план остаётся plan-only, поэтому `/do` требует отдельного свежего решения. Отчёт не переименовывает исходный transport failure в успех: отдельно показывает candidate, incident/accepted-input, успешную локальную запись и состояние каждой remote publication. Incident-v2 метки и строки Assumptions не удалять: по ним повторная публикация отличает восстановленный ввод от обычной доставки.
2. `/do ACME-342 [ACME-343 …]` — parent сначала резервирует все допустимые ключи, затем поднимает отдельный фоновый coordinator на каждый ключ под общим лимитом, в `work/<KEY>/`: новых вкладок и пан нет, главный чат остаётся доступен. Ошибка одного ключа не останавливает siblings. Каждый coordinator создаёт ворктри на каждый репозиторий из своего плана, выполняет проверки, независимое ревью, правки, формат и PR; после `pnpm record-report` (стадия `review`) шлёт terminal result. Когда все ключи terminal, parent присылает один ordered aggregate. Координатор и его работающие дети видны в widget над редактором главного чата. Прогресс — чекбоксы в `work/ACME-342/progress.md`; прерванный run продолжает тот же branch/PR и не стирает неизвестный diff.
3. `/review ACME-342 [заметка]` — приёмка в новом tab (`--split` — split): стенд штатным dev-рецептом проекта (браузерные расширения — папкой в `~/Downloads`), прогон приёмочного чек-листа плана по пунктам с вердиктом на каждый. Замечания записываются дословно, список читается тебе назад до того, как станет планом доработки; каждое замечание воспроизводится и локализуется до файлов. На машине, где /do не бежал, панель ревью сама начинает с `pnpm adopt ACME-342` — стенд и строка review собираются из наблюдаемых фактов (план в `home/knowledge/`, ветки, PR).
4. Замечания есть → после согласования плана ты даёшь финальный вердикт «на доработку». Зарегистрированный review runtime по raw interactive input создаёт одно parent-owned полномочие: `pnpm accept ACME-342 --rework <путь>` передаёт parent точный regular UTF-8 plan из knowledge, parent записывает path/content/scope/repositories и запускает один `/do` с do-моделью без второго confirm при обоих `workflowApproval`. Папка, ветки и PR сохраняются. Review закрывается только после ready и успешного work ACK; record/model/queue/handshake/ACK failure оставляет её открытой с path/hash/stage/reason и не retry-ится старым вердиктом. Ошибка close показывается отдельно от уже запущенного do. Чисто → панель выполняет `pnpm accept ACME-342`; do и auto-close нет, строка уходит из очереди, папка остаётся для /ship, а review закрываешь ты.

Мерж делает /ship — набранная команда и есть твоё слово на мерж. По принятому тикету (или нескольким): `/ship ACME-342 [ACME-343 …]` после одного exact permit и optional UI-подтверждения запускает независимый фоновый coordinator на каждый допустимый ключ без вкладок. Они параллельно обновят ветки от базы, разведут конфликты, допушат в те же PR и дождутся зелёного CI. Непосредственный fresh gate-and-merge идёт только через parent-owned `coordinator_merge` и сериализуется для одинакового canonical repository/base: parent повторно читает target/head точного PR, выполняет per-part gate и тот же SHA передаёт в match-head merge. Каждый ключ отдельно пишет «отгружено» и удаляет `work/<KEY>`; blocker одного не отменяет siblings. Parent шлёт terminal result по мере завершения и один ordered aggregate после всех ключей. Стадия не меняется.

## Повторный запуск, подтверждения, модель

При включённых duplicateDo/duplicateMode второй запуск по тому же тикету не поднимает дубль; при off отдельные ordinary runs разрешены, но каждый do всё равно требует нового single-use approval. Review→rework принудительно остаётся одним key run и одним retained startup outcome независимо от этих flags: повтор того же accept получает прежний run/outcome, fresh verdict после pre-start failure создаёт новую operation. Один list request публикует все immediate ACK/refusal до fast terminal results; cancel list останавливает каждый активный key run, cancel key не трогает siblings. Retained `pnpm spawn` и `pnpm ship` обращаются к живому parent runtime через owner-only socket и отказывают без точной session binding. Через твоё подтверждение проходит только `/ship` — он мержит; do, review, worklog и split запускаются без диалога. Подтверждение и typed `/ship` проверяет backend, а страж (`src/bash-guard.ts`) режет циклы ожидания и запуск приложений на этапе кода. Отдельный research code consent для точной правки не зависит от этого правила и от YOLO.

Общий приоритет: `--model` в команде → переопределение мода в паспорте → умолчание проекта в паспорте → `pool[mode]` → громкий отказ. Пул читается только когда запрос паспортов по tracker key или org вернул ноль строк; disagreement эффективных значений или найденный `NULL` — ошибка паспортов и пулом не маскируется. Модель запуска называешь в приписке: `/do ACME-231 запусти на gpt-6-astra, задача сложная` — оркестратор передаст её background coordinator; флаг перекрывает паспорт и ничего не меняет в конфиге. Без флага паспорт отвечает по моду: `plan, review, do, ship, worklog, note, research`. `/plan` для явного списка ключей выбирает модель отдельно по этому приоритету для каждого ключа; mixed input остаётся одним интервью с моделью первого ключа, а без ключей сразу спрашивает `pool.plan`.

`pnpm set-model <KEY> [<модель>] [<мод>=<модель> …]` меняет у всех паспортов ключа разом что названо — умолчание проекта, отдельные моды или всё сразу — и не теряет остального. Снять переопределение мода можно только повторным `add-project` без этого токена: его upsert перезаписывает карту целиком.

`home/pool.json` — partial map рядом с `projects.json`: `{"plan":"<паттерн>","review":"<паттерн>","do":"<паттерн>","ship":"<паттерн>","worklog":"<паттерн>","note":"<паттерн>","research":"<паттерн>"}`. Можно настроить только используемые ключи. Запуск без тикета (`/plan <проблема>`, `/note <тема>`, свободный research) спрашивает пул сразу; keyed plan/review/do/ship/worklog — только при нулевом наборе подходящих паспортов. Файла или запрошенного мода нет — запуск отказывает с точным путём и mode; литерала модели в коде нет.

## Исследование без тикета

`/research [--split] [--project <org/repo|repo|KEY>] [--model <m>] [--topic] <тема>` поднимает независимый tab по умолчанию, с `--split` — split и не меняет очередь, стадии, планы или ворктри. Без `--project` первый токен сопоставляется с паспортом; `--topic` оставляет его частью свободной темы. Для проекта модель берётся в порядке `--model`, research override паспорта, default паспорта; свободная тема берёт `pool.research` из `home/pool.json`.

Вкладка читает клон и разрешённые web/tracker источники, автоматически сохраняет артефакты в `home/knowledge/<org>/<repo>/research/` (свободная тема — в `home/notes/`), но не закрывается сама. Ответы и пути артефактов остаются в research-вкладке; отчёт в главный чат отправляется только по отдельному явному запросу инженера. Создание issue происходит только по просьбе. Каждая конкретная правка clone требует отдельного TUI consent с полным target и diff даже с `-a`/YOLO; согласие не разрешает shell, commit, push или другую правку. Bounded shell/MCP/script допускают только перечисленные операции чтения и создания issue; это контроль harness, не OS sandbox.

## Прочее

- `pnpm pr-link ACME-342 <url>…` — ссылка на PR комментарием в тикет.
- `pnpm say [--to <pane>] "<текст>"` — отправка сообщения в inbox панели (обратный адрес по `HERDR_PANE_ID`).
- `pnpm drop ACME-342` — явное снятие тикета с очереди; ворктри, ветки, PR и папка задачи не трогаются. PR смержен руками мимо /ship → `pnpm drop <KEY>` + `rm -rf work/<KEY>`.
- `pnpm stage ACME-342 <stage> [путь-к-плану] [--force]` — ремонт из главного чата, только с `--force`; легальные переходы делают свои команды (`plan`, `spawn`, `record-report`, `accept`). `pnpm close-mode <ship|do> ACME-342` оставлен только как безопасный compatibility-ответ: background run не имеет вкладки.
- `/journal` — запись в `home/journal/YYYY-MM.md`: только реальные итоги и решения с их «почему», по одной записи на проект.
- `/worklog acme-eu [заметка]` — новый tab по умолчанию (`--split` — split): называешь период словами («залогаем 15 августа», «за неделю»), он собирает следы (журнал, коммиты, календарь), предлагает раскладку часов по тикетам, ты правишь — подтверждённые строки уходят в YouTrack. Панель закрываешь ты. Итоги тикетов («дата тикет запланировано/сделано/принято») команды дописывают в `home/journal/YYYY-MM.md` сами.
- `/note [тема]` — новый tab по умолчанию (`--split` — split): беседа о пуле или проекте без права правок — гвард режет всё пишущее вне `home/notes/`. «Сохрани» → md-заметка в `home/notes/` + `pnpm note-save` (коммит и пуш только `home/notes/`), «выгрузи в гист» → secret-гист со ссылкой в панели. Панель закрываешь ты.
- `pnpm test` — смоук за секунды; `pnpm metrics` — качество диалога по журналам.
- Канарейка `[k7x2]` — каждый ответ любой сессии этого корня (главный чат, паны, вкладки /do) начинается с литерального маркера `[k7x2]`; правило стоит в хвосте AGENTS.md.
  Маркер пропал или исказился хотя бы на символ — контекст сессии деградировал, перезапусти её.
  Никакой автоматики за маркером нет — это визуальный сигнал, реакция на него твоя.

## Guard policy

Единственный источник policy — `<engine-root>/.pi/settings.json`; он перечитывается перед каждым guarded action, CLI-переходом и dispatch subagent. Все поля необязательны:

```json
{
  "guardPolicy": {
    "yolo": false,
    "workflowApproval": true,
    "guards": {}
  }
}
```

Реестр keys: `settingsWrite`, `noteFileWrite`, `wait`, `noteShellWrite`, `codingLaunch`, `massKill`, `homeDelete`, `shipConfirmation`, `doCompletion`, `modeOwnership`, `transitionCaller`, `transitionTicket`, `transitionSource`, `spawnCaller`, `stageCaller`, `stageForce`, `duplicateDo`, `duplicateMode`, `reportTarget`, `projectAgentConfirmation`, `parallelTaskLimit`, `parallelConcurrencyLimit`, `detachedLimit`.

`yolo: true` выключает optional action guards и `workflowApproval`; явный `guards.<id>: true` сильнее preset. Например, `{ "guardPolicy": { "guards": { "wait": false } } }` выключает только wait; `{ "guardPolicy": { "yolo": true, "guards": { "settingsWrite": true, "shipConfirmation": true } } }` возвращает эти два ограничения. Удаление overrides и `yolo: false` возвращают legacy defaults. Повреждённая policy явно блокирует action с путём и причиной; guards — эвристические ограничения, не sandbox.

`workflowApproval: false` снимает промежуточные текстовые паузы только внутри уже делегированной задачи. Scope, quality gates, готовый PR с `record-report`, корректные данные и введённый инженером `/ship` остаются обязательными. `shipConfirmation: false` снимает только второй UI-вопрос, не создаёт полномочие на merge. Разрешённые дубли получают отдельные run ID; отчёт передаёт их parent runtime. Background coordinators не имеют вкладки для close-mode.

### Runtime snapshot и approval

Один `readRuntimeSettings` читает policy и subagent limits до guarded decision; принятый ordinary batch сохраняет snapshot до конца. Следующее решение видит изменение файла без reload; отдельный transition write после подготовки перечитывает settings и всегда сохраняет expected-stage CAS. Task-local settings, settings.local.json, паспорт, environment и tool arguments не являются overrides. Child settings содержат только абсолютные engine extensions, не копию limits.

Приоритет: явный `guards.<id>` и workflowApproval сильнее yolo; затем legacy defaults. Все guards и workflowApproval по умолчанию true. Limits: maxParallelTasks=8, maxConcurrency=4, maxDetached=8. Если задан только maxParallelTasks, соседние defaults становятся min(4, parallel) и max(8, parallel). Unknown owned fields, non-boolean policy, non-integer/positive limits, broken/unreadable JSON и несовместимые limits блокируют action с абсолютным source path. Другие Pi-owned root fields не проверяются.

Например, `{"guardPolicy":{"yolo":true,"workflowApproval":true,"guards":{"wait":true}},"subagent":{"maxParallelTasks":2}}` оставляет wait и остановку после плана включёнными при остальных optional guards off. Off убирает ровно один отказ: modeOwnership/spawnCaller не меняют identity/socket/session; caps не убирают accounting; doCompletion off блокирует idle coordinator без synthetic turn, но не даёт ложный success. Scope, auth/data, CAS, ready/CI/independent review/report/outcome и exact ship permit обязательны всегда. Loaded ship guard запрещает прямые CLI и GitHub API merge paths: merge проходит только через parent-owned `coordinator_merge`, который проверяет live run и exact prepared part, сериализует canonical repository/base, повторно читает PR target/head, выполняет per-part gate и передаёт этот SHA в `--match-head-commit`; эта граница не отключается YOLO.

Обычный `/plan KEY` всегда заканчивается записанным планом — даже при workflowApproval=false. Только явное plan+do в том же raw interactive input создаёт pending parent receipt. После `pnpm plan` parent перечитывает фактическую DB row и regular file: false связывает receipt с content/scope/repositories и запускает один do, true оставляет готовый план и требует нового approval. Нет живого parent — запись плана успешна, auto-do отсутствует; output говорит об этом явно. Плановая pane регистрируется parent-ом и не создаёт authority.

Последующий `/do KEY` или однозначное NL-согласование создаёт новый parent-owned single-use receipt без второго confirm. Exact key, recorded path, SHA-256 bytes, scope/repository digest, parent session/runtime и generation обязательны. Изменение плана требует нового approval. Stop/cancel, смена session/fork/reload отзывают authority; transcript её не восстанавливает. Active owned children и correlated reviews продолжают тот же cycle при неизменном плане. NL extraction использует configured model без tools и literal evidence spans текущего raw input; deterministic tests доказывают provenance/handoff, не универсальное понимание языка.

Review rework использует отдельный receipt и registered worker identity, а не main `DoAuthorityStore`: launcher связывает run с точными tab/split IDs, worker session/runtime/PID/starttime и parent chain. Только raw interactive TUI input этого runtime может создать verdict; CLI/RPC/tools/reports/transcript — нет. Вопрос, цитата, отрицание, условие, замечание или согласие с отдельным пунктом дают `none`; stop и новый input инвалидируют ещё не переданный generation. После work ACK do живёт независимо от review.
