# Как пользоваться yokemate

Главный чат — сессия pi в корне репозитория, открытая в herdr. Команды ниже набираются в нём. Стадию в базе (`yokemate.db`) записывает та панель, где родился результат: команды сами проверяют штамп панели, допустимость перехода и текущую стадию. Главный чат остаётся входом для ремонта (`pnpm stage … --force`) и закрывает вкладки по уведомлениям.

## Подключение проекта

```bash
pnpm add-project <путь-к-клону> --tracker <org:KEY> --model <m> [--model <мод>=<m> …] [--figma <mcp>] [--figma-file <url>] [--subsystem <значение>]
```

Паспорт репозитория попадает в базу, знание из его `.yoke/` импортируется один раз в `home/knowledge/<org>/<repo>/`.

Паспорта живут и в манифесте `home/projects.json`: `pnpm export-projects` выгружает их туда разом (первое заполнение и ремонт), `pnpm import-projects [--only <org/repo>]` восстанавливает клоны в `projects/<org>/<repo>` и паспорта из манифеста — существующие паспорта не трогаются. Новую машину поднимает `scripts/bootstrap.sh` — идемпотентен, что остаётся ручным (`.env.local`, `home/`, `gh auth login`, ключи), называет в финальной сводке. `home/` поднимается клоном по адресу из `YOKEMATE_HOME_REMOTE`; без переменной bootstrap его не создаёт и называет шаг в сводке.

## Обзор

- `pnpm on-me [org] [PROJECT] [--repo <name>] [--stage <values>] [--stages] [--all] [--verbose]` — неразрешённые тикеты на мне, прямо из трекеров, по репозиториям.
- `pnpm queue [planned|me]` — локальная очередь; синк с трекерами при каждом чтении.
- `pnpm warmup` / `/warmup` — дайджест пула (очередь, живые `work/`, хвост журнала), офлайн и без синка; хук `session_start` вставляет его сам на старте сессии.

## Круг тикета

1. `/plan ACME-342 [заметка]` или `/plan <проблема>` — инлайн в главном чате: разведка кода и написание плана — в сабагентах (`plan-scout`, `plan-writer`), вопросы к тебе — в той же ленте, по одному с выбором опций (немного вопросов, только меняющие реализацию, каждый с рекомендацией). Вход с проблемой сначала проходит интервью и валидацию пакета («Заводим?») — тикеты создаются в YouTrack до планов. Итог: детальный план в `home/knowledge/<org>/<proj>/ai/<KEY>-<slug>/`, по которому /do работает без переспросов — шаги с файлами и проверкой на каждый, допущения, out of scope, критерии приёмки; стадию `planned` записывает `pnpm plan`. Нерешаема на данных тикета — плана нет, отчёт называет недостающее. Ни новой паны, ни вкладки не появляется. На большом экране `/split plan <аргументы>` поднимает тот же /plan в сплите — несколько планирований параллельно; сплит закрываешь ты.
2. `/do ACME-342` — вкладка задачи в `work/ACME-342/`: ворктри на каждый репозиторий из плана, код по шагам плана с проверкой на каждом (где есть тестовый набор — тест до кода), затем собственные проверки проекта, независимое ревью свежим взглядом (его линзы включают простоту диффа и свежесть доков) с правкой находок и повторной проверкой, автоформат, PR на репозиторий; результат вкладка записывает сама (`pnpm record-report`, стадия `review`) и шлёт уведомление в чат. Прогресс — чекбоксы в `work/ACME-342/progress.md`, перезапуск вкладки продолжает с первого неотмеченного.
3. `/review ACME-342 [заметка]` — приёмка в сплите: стенд штатным dev-рецептом проекта (браузерные расширения — папкой в `~/Downloads`), прогон приёмочного чек-листа плана по пунктам с вердиктом на каждый. Замечания записываются дословно, список читается тебе назад до того, как станет планом доработки; каждое замечание воспроизводится и локализуется до файлов. Сплит закрываешь ты. На машине, где /do не бежал, панель ревью сама начинает с `pnpm adopt ACME-342` — стенд и строка review собираются из наблюдаемых фактов (план в `home/knowledge/`, ветки, PR).
4. Замечания есть → панель приёмки сама выполняет `pnpm accept ACME-342 --rework <путь>` (путь — план доработки, который она только что записала) → `/do ACME-342` снова: та же папка, ветка и PR. Чисто → она же выполняет `pnpm accept ACME-342` — строка уходит из очереди, а папка задачи остаётся: в ней работает /ship и удаляет её после мержа.

Мерж делает /ship — набранная команда и есть твоё слово на мерж. По принятому тикету (или нескольким): `/ship ACME-342 [ACME-343 …]` — вкладка обновит ветки от базы, разведёт конфликты, допушит в те же PR, дождётся зелёного CI, смержит каждый PR, запишет в журнал «отгружено» и удалит `work/<KEY>`; пачка мержится по очереди — каждый следующий обновляется от базы, куда уже вошёл предыдущий. Стадия не меняется, вкладку закрывает главный чат (`pnpm close-mode ship ACME-342`).

## Повторный запуск, подтверждения, модель

Второй запуск режима по тому же тикету не поднимает дубль — команда печатает, где стоит первый. Обратный адрес выводится из `HERDR_PANE_ID` самой панели — отдельной переменной для него больше нет; spawn, review, ship, worklog и split plan отказываются только вне herdr-сессии. Через твоё подтверждение проходит только `pnpm ship` в любой форме запуска — он мержит; spawn, review, worklog и split поднимаются без диалога. Подтверждение спрашивает страж (`src/bash-guard.ts`), он же режет циклы ожидания и запуск приложений на этапе кода.

Приоритет один и в этом порядке: `--model` в команде → переопределение мода в паспорте → умолчание проекта в паспорте → `home/pool.json` для запусков без тикета. Модель запуска называешь в приписке: `/do ACME-231 запусти на gpt-6-astra, задача сложная` — оркестратор передаст вкладке `--model`; флаг перекрывает паспорт и работает для всех режимов с паной, а в конфиге ничего не меняет. Без флага паспорт отвечает по моду поднимаемой панели: `plan, review, do, ship, worklog, note`. Инлайн-`/plan` идёт на модели самого главного чата.

`pnpm set-model <KEY> [<модель>] [<мод>=<модель> …]` меняет у всех паспортов ключа разом что названо — умолчание проекта, отдельные моды или всё сразу — и не теряет остального. Снять переопределение мода можно только повторным `add-project` без этого токена: его upsert перезаписывает карту целиком.

У запуска без тикета (`/plan <проблема>`, `/note <тема>`) ключа нет, спросить паспорта не о чем — модель приходит из `home/pool.json`, плоской карты `{"plan": "<паттерн>", "note": "<паттерн>"}` рядом с `projects.json`. Файла или нужного мода там нет — панель не поднимается, отказ называет путь и форму; литерала модели в коде не осталось нигде.

## Прочее

- `pnpm pr-link ACME-342 <url>…` — ссылка на PR комментарием в тикет.
- `pnpm say [--to <pane>] "<текст>"` — отправка сообщения в inbox панели (обратный адрес по `HERDR_PANE_ID`).
- `pnpm drop ACME-342` — явное снятие тикета с очереди; ворктри, ветки, PR и папка задачи не трогаются. PR смержен руками мимо /ship → `pnpm drop <KEY>` + `rm -rf work/<KEY>`.
- `pnpm stage ACME-342 <stage> [путь-к-плану] [--force]` — ремонт из главного чата, только с `--force`; легальные переходы делают свои команды (`plan`, `spawn`, `record-report`, `accept`). Вкладки закрывает `pnpm close-mode <ship|do> ACME-342` по уведомлению.
- `/journal` — запись в `home/journal/YYYY-MM.md`: только реальные итоги и решения с их «почему», по одной записи на проект.
- `/worklog acme-eu [заметка]` — сплит рядом с чатом: называешь период словами («залогаем 15 августа», «за неделю»), он собирает следы (журнал, коммиты, календарь), предлагает раскладку часов по тикетам, ты правишь — подтверждённые строки уходят в YouTrack. Сплит закрываешь ты. Итоги тикетов («дата тикет запланировано/сделано/принято») команды дописывают в `home/journal/YYYY-MM.md` сами.
- `/note [тема]` — сплит рядом с чатом: беседа о пуле или проекте без права правок — гвард режет всё пишущее вне `home/notes/`. «Сохрани» → md-заметка в `home/notes/` + `pnpm note-save` (коммит и пуш только `home/notes/`), «выгрузи в гист» → secret-гист со ссылкой в панели. Сплит закрываешь ты.
- `pnpm test` — смоук за секунды; `pnpm metrics` — качество диалога по журналам.
- Канарейка `[k7x2]` — каждый ответ любой сессии этого корня (главный чат, паны, вкладки /do) начинается с литерального маркера `[k7x2]`; правило стоит в хвосте AGENTS.md.
  Маркер пропал или исказился хотя бы на символ — контекст сессии деградировал, перезапусти её.
  Никакой автоматики за маркером нет — это визуальный сигнал, реакция на него твоя.
